# FleetManager Server

Веб-система управления парком компьютеров с интеграцией Ansible: CMDB хостов, инвентаризация ПО, диагностика подключения, запуск плейбуков через Celery, Key Store для credentials, JWT+TOTP аутентификация, учёт и удалённое обновление версий агента.

## Связанные репозитории

- [FleetManager-Agent](https://github.com/Xorizo-n/FleetManager-Agent) — Windows-агент, который шлёт heartbeat и инвентаризацию на этот сервер.
- [RTF_OOD_AnsiblePlaybooks](https://github.com/kozlov174/RTF_OOD_AnsiblePlaybooks) — плейбуки установки ПО, которые сервер запускает через Ansible Runner.

## Структура

```
backend/    FastAPI + SQLAlchemy + Alembic + Celery
frontend/   React + TypeScript + Tailwind (Vite)
ansible/    плейбуки Fleet Manager, включая scan_software.yaml
```

## Запуск

```bash
cp .env.example .env
# сгенерировать секреты и вписать в .env:
openssl rand -hex 32                                                              # JWT_SECRET_KEY
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"  # CREDENTIAL_ENCRYPTION_KEY

docker compose build
docker compose up -d
```

- Frontend: https://localhost (самоподписанный сертификат — браузер попросит подтвердить), http://localhost перенаправляет туда
- Backend API + Swagger: http://localhost:8000/docs

Первый запуск: зарегистрируйте пользователя через `/auth/register` (первый зарегистрированный пользователь становится `admin`), затем привяжите TOTP на экране логина по QR-коду.

## Вход доменной учётной записью (LDAP)

Кроме локальных пользователей, в Fleet Manager входят учётными записями домена at.urfu.ru (`backend/services/ldap_auth.py`). Логин — в любой привычной форме: логин Windows (`Mikhail.Rapoport`, `AT\Mikhail.Rapoport`, `Mikhail.Rapoport@at.urfu.ru`), имя записи (cn), UPN или почта (`m.i.rapoport@urfu.ru`) или её левая часть (`m.i.rapoport`). Формы пробуются от точной к менее точной; если под введённым именем несколько записей, вход отклоняется с просьбой войти логином Windows. Без служебной учётной записи работают только логин Windows и полный UPN — искать запись до входа некому. Пользователь Fleet Manager всегда заводится под логином Windows, в какой бы форме ни входил.

- **Настройки** — Администрирование → «Вход через домен» (только администратор): включение, контроллеры, служебная учётная запись, группы ролей (поиск групп в домене по имени), проверка до сохранения — служебная запись, группы с числом участников и роль конкретного пользователя. Сохранённое хранится в БД (`ldap_settings`, пароль зашифрован `CREDENTIAL_ENCRYPTION_KEY` и наружу не отдаётся) и важнее `LDAP_*` из `.env`; `.env` — значения до первого сохранения. CA, фильтр поиска пользователя и таймаут — только в `.env`.
- **Соединение.** Только LDAPS (`ldaps://at.urfu.ru`, 636) с проверкой сертификата контроллера по корневому «Ural Federal University Root CA» — `backend/trust/urfu-root-ca.pem`, попадает в образ. `ldap://` в `LDAP_URL` работает через StartTLS.
- **Пароль** проверяет сам домен (bind от имени пользователя); Fleet Manager его не хранит. Пустой пароль отклоняется до обращения к домену: AD считает такой bind анонимным и «успешным».
- **Доступ и роль — по группам AD** (на странице настроек или `LDAP_ADMIN_GROUPS`, `LDAP_OPERATOR_GROUPS`, `LDAP_VIEWER_GROUPS`: DN через `;`; вложенные группы учитываются). Действует старшая роль. Не состоит ни в одной группе — не входит: в домене есть и студенты, поэтому «любой пользователь домена» не пускается никогда, а без заданных групп вход через домен закрыт целиком.
- **Пользователь** создаётся при первом входе (источник «домен» на странице «Пользователи»), имя, email и роль по группам обновляются при каждом входе. Администратор может назначить доменному пользователю другую роль (например, повысить оператора до администратора) — ручная роль важнее групп и сохраняется при входе; выбрать снова роль по группам — вернуть её группам. Доступ всё равно даёт только членство в группе. Пароль доменной записи в Fleet Manager не меняется. Второй фактор (TOTP) — как у локальных. Блокировка в Fleet Manager действует и для доменной записи.
- **Служебная учётная запись** (только чтение) необязательна для входа, но нужна для поиска групп и проверки на странице настроек. С ней при каждом обновлении токена (раз в 15 минут) сервер перепроверяет, что запись не отключена и не исключена из групп, и сразу закрывает доступ; без неё доступ живёт до истечения refresh-токена (`REFRESH_TOKEN_EXPIRE_DAYS`). Если домен недоступен, уже вошедших это не выбрасывает.
- **Локальные пользователи** остаются: локальная запись с тем же именем важнее доменной — это аварийный вход администратора, когда домен недоступен.

## Деплой на прод

Прод (`10.40.240.154`) — git-клон этого репозитория в `/opt/fleet-manager`, ветка `main`. Файлы на сервере не правятся: изменения идут через PR, а `git status` там должен оставаться чистым. `.env`, `_backup/` и `_logs/` в git не попадают.

```bash
cd /opt/fleet-manager
git pull --ff-only
docker compose build backend celery celery-beat frontend
docker compose up -d backend celery celery-beat frontend
docker builder prune -f
```

- Миграции применяются сами: backend при старте выполняет `alembic upgrade head`.
- PostgreSQL и Redis при этом не пересоздаются.
- Последняя команда обязательна: на сервере диск 15 ГБ, и кэш сборки (особенно когда заново собирается слой с `pip install`) заполняет его до конца.
- Перед `up -d` проверьте, что celery ничего не выполняет (`docker exec fleet-manager-celery-1 celery -A celery_app.celery_app inspect active`): пересоздание контейнера обрывает запущенные плейбуки.

### Время на сервере

- Часовой пояс хоста — `Asia/Yekaterinburg` (`timedatectl set-timezone Asia/Yekaterinburg`). Часы аппаратные в UTC.
- Синхронизация — `systemd-timesyncd`. Серверы времени задаются отдельным файлом `/etc/systemd/timesyncd.conf.d/fleet-manager.conf`, не в git:

  ```ini
  [Time]
  NTP=ntp.urfu.ru ntp1.vniiftri.ru ntp2.vniiftri.ru
  FallbackNTP=ntp.ix.ru time.google.com
  ```

  `ntp.urfu.ru` — в сети УрФУ (задержка < 1 мс). ВНИИФТРИ — государственный эталон времени, stratum 1. Проверка: `timedatectl timesync-status`.
- Cron в расписаниях плейбуков — местное время: `SCHEDULE_TIMEZONE`, по умолчанию `Asia/Yekaterinburg`. «0 9 * * *» — 9:00 по Екатеринбургу.

### Резервное копирование БД

- Каждый день в 23:00 по времени сервера `backup-db.sh` снимает `pg_dump` в `/opt/fleet-manager/_backup/daily/fleet_manager-ГГГГММДД-ЧЧММ.sql.gz`. Хранится 30 дней (`KEEP_DAYS`), старые удаляются. Каталог доступен только root: в дампе хэши паролей и зашифрованные учётные данные.
- Дамп публикуется, только если архив целый и `pg_dump` дописал финальную строку; иначе в журнал пишется `FAIL`. Журнал — `_logs/backup-db.log`.
- Установка (из корня клона на сервере):

  ```bash
  chmod 750 backup-db.sh
  install -m 644 backup-db.cron /etc/cron.d/fleet-manager-backup
  ```

- Восстановление — в отдельную БД, рабочая не трогается:

  ```bash
  docker compose exec -T postgres createdb -U fleet fleet_restore
  zcat _backup/daily/fleet_manager-<дата>.sql.gz | docker compose exec -T postgres psql -U fleet -d fleet_restore
  ```

- Эти бэкапы лежат на том же системном диске, что и сама БД: от потери диска целиком они не спасают. Для этого есть копии вне ВМ.

### Копии вне ВМ

Без БД и `.env` сервера доступ ко всем ПК теряется. Агенты получают 401 и сами заново не регистрируются, а SSH-ключи ПК хранятся в БД зашифрованными ключом из `.env`. Поэтому копии уходят за пределы ВМ (`backend/services/offsite_backup.py`):

- **Хранилище:** restic по SFTP. Хранилище, логин, пароль SFTP и пароль шифрования копий задаются в «Администрирование → Резервные копии». Пароли хранятся в БД зашифрованными и наружу не отдаются. Ключ SSH хранилища закрепляется при сохранении.
- **Расписание** (воркер Celery):
  - каждые 4 часа — дамп БД вместе с `.env`, `certs/` и локальными плейбуками;
  - ночью в 02:30 — `/mnt/soft-share`;
  - по воскресеньям в 05:00 — проверка восстановления: `restic check`, восстановление дампа во временную БД `fm_restore_check`, сверка с рабочей БД, расшифровка учётных данных ключом из скопированного `.env`, затем `prune`.
- `.env` и `certs/` смонтированы в воркер только на чтение (`/mnt/fleet-config`). Образ backend содержит `restic` и `pg_dump` 15 из репозитория PGDG — той же версии, что и сервер БД.
- Статус виден на странице «Резервные копии» и на «Мониторинге». Тревога поднимается, если копия БД старше `OFFSITE_DB_MAX_AGE_HOURS` (6 ч) или проверка восстановления не прошла.
- Восстановление на новой ВМ — пошагово в [docs/disaster-recovery.md](docs/disaster-recovery.md). Пароль шифрования копий нужно хранить и вне сервера: без него копии не открыть.

## HTTPS и порты

| Порт | Что |
|---|---|
| 443 | сайт и API по HTTPS |
| 80 | перенаправление на HTTPS |
| 8080 | API для агентов по HTTP; интерфейс с него перенаправляется на HTTPS |

- **Агенты остаются на 8080.** В `agent.json` у них `http://<сервер>:8080`, и сервер встраивает этот же адрес в установщики (`AGENT_PUBLIC_URL`). Перенаправить агентов на HTTPS нельзя: и HttpClient агента, и `Invoke-WebRequest` при удалённом обновлении теряют заголовок `Authorization` при редиректе. Закрывать 8080 можно только после того, как все агенты получат новый адрес.
- **Сертификат** — `certs/fleet.crt` (с цепочкой) и `certs/fleet.key` в `/opt/fleet-manager`, в git не попадают. Пока их нет, контейнер frontend при старте создаёт самоподписанный на имена из `TLS_SELF_SIGNED_SAN` (по умолчанию `IP:10.40.240.154`) и дальше его не перевыпускает.
- **Замена на сертификат от УЦ УрФУ:** положить файлы под теми же именами и выполнить `docker compose restart frontend`. Корневой «Ural Federal University Root CA» есть на ПК обоих доменов (at.urfu.ru и rtf.ustu), поэтому браузерам и агентам больше ничего не нужно.

## Пароли локального администратора

Плейбук `set_local_admin_password.yml` (репозиторий плейбуков) задаёт `.\admin` пароль аудитории — тот же, что AutoDomain при вводе в домен.

- **Где лежат:** `room-passwords.csv` и `room-passwords.key` из AutoDomain кладутся в `/opt/fleet-manager/secrets/room-passwords/` (каталог `700`, файлы `600`, в git не попадают). В воркер Celery каталог смонтирован только на чтение как `/mnt/room-passwords`.
- **Как работает:** пароль расшифровывается в воркере, на ПК передаётся только пароль его аудитории — временным файлом, который сразу удаляется.
- **Обновление:** после смены паролей через `RoomPasswords.cmd` скопировать новый CSV поверх старого. Перезапуск не нужен.
- В копии вне ВМ этот каталог не входит: оригинал хранится у AutoDomain.
- Плейбук с доступом к `/mnt/room-passwords` может прочитать любой, кто может запускать или редактировать плейбуки в Fleet Manager, поэтому выдавайте эти права только администраторам.

## Пробуждение по сети и выгрузка реестра

- **MAC-адреса.** Агент с версии 2026.10.12 сообщает сетевые адаптеры: имя, MAC, IPv4 с маской. Основной MAC — у адаптера, через который ПК пришёл на сервер. Он виден в карточке ПК, в выгрузке реестра и в inventory Ansible (`mac_address`).
- **«Разбудить».** Кнопка в карточке выключенного ПК, для нескольких ПК — в меню «Ещё». Сервер в другой сети, поэтому магический пакет отправляет по SSH включённый ПК из той же подсети (`services/wake_on_lan.py`), если он недоступен — следующий. Затем до 7 минут сервер ждёт ответа по SSH или heartbeat и пишет итог по каждому ПК.
- **Подготовка ПК.** Её делает установщик агента: проводная сетевая карта может будить компьютер, «Быстрый запуск» выключен. **Пробуждение по сети должно быть разрешено в BIOS** — это удалённо не сделать.
- **Диски и скорость сети.** Агент с версии 2026.10.15 присылает в каждом heartbeat заполненность локальных несъёмных дисков (`hardware.disks`) и скорость линка каждого адаптера (`link_speed_bps`). Карточка ПК показывает все диски и адаптеры, реестр в режиме «Железо» — самый заполненный диск и скорость основного адаптера; по обеим колонкам можно сортировать. Диск от 80 % — жёлтый, от 90 % — красный; проводной линк медленнее гигабита — жёлтый (обычно кабель или порт). Старые агенты этих данных не присылают — у них колонки пустые до обновления.
- **Выгрузка.** Меню «⋯» на странице хостов → «Выгрузить реестр ПК в CSV» (`GET /hosts/export.csv`): имя, IP, MAC, группа, статус, агент, ОС, оборудование. Разделитель `;` и UTF-8 с BOM — открывается в Excel как есть.

## Обои рабочего стола и экрана блокировки

Страница «Обои»: каталог изображений, что стоит на ПК сейчас, назначения и смена по расписанию (`services/wallpapers.py`, `routers/wallpapers.py`).

- **Каталог.** JPEG, PNG или BMP до 30 МБ загружаются на сервер в `WALLPAPER_DIR` (по умолчанию `/mnt/soft-share/wallpapers`, имя файла — SHA-256). В БД хранятся метаданные и миниатюра 320 px. Одинаковое изображение второй раз не загрузится. Удалить можно только изображение, которое никому не назначено и не стоит в расписании.
- **Назначение.** Делается ПК или группе, рабочий стол и экран блокировки отдельно. У ПК действует своё назначение, иначе — ближайшей группы вверх по дереву (аудитория → этаж → корпус). Назначение или снятие у группы действует на всю группу: свои назначения того же вида у её аудиторий и ПК снимаются (диалог предупреждает, сколько их). Чтобы аудитории остались свои обои, их назначают после назначения корпуса. Если ничего не назначено, сервер обоями не управляет, и на ПК остаётся то, что задано в образе. Массовая замена — кнопка «Назначить обои…» или «Ещё → Обои…» для выбранных ПК в реестре. Корпус, этаж или аудитория, выбранные целиком, получают назначение на группу, его получат и новые ПК в ней.
- **Смена в заданное время.** При назначении выбирается «В заданное время». Сервер раз в минуту (`apply-wallpaper-schedules` в celery beat) применяет смены, чьё время пришло. Запланированную смену можно отменить.
- **Доставка.** Агент 2026.10.18+ получает назначенные обои в ответе на heartbeat. Изображение он скачивает сам своим токеном (`GET /api/agent/wallpapers/{id}`) и проверяет SHA-256.
  - **Куда пишет.** В образе обои и экран блокировки заданы локальной групповой политикой (`C:\Windows\System32\GroupPolicy\…\Registry.pol`; на SU5/SU7 экран блокировки ещё и через PersonalizationCSP), а не доменной GPO. Поэтому агент меняет записи именно там (экран блокировки — `LockScreenImage`, рабочий стол — пользовательская политика `Wallpaper` для всех пользователей), увеличивает версию в `gpt.ini` и сразу пишет те же значения в реестр.
  - **Открытый сеанс.** Трей обновляет рабочий стол без выхода из системы.
  - **Снятие назначения.** Исходные значения образа агент сохраняет при первом изменении и возвращает, когда назначение снято.
  - **Ограничение редакций.** Политика экрана блокировки работает в редакциях Enterprise и Education (в том числе Pro Education), в обычной Pro — нет.
- **Что стоит сейчас.** Агент в каждом heartbeat сообщает путь и SHA-256 текущих обоев (`hosts.wallpaper_state`). Для изображений не из каталога (обои образа) сервер один раз запрашивает у агента миниатюру (`observed_wallpapers`). На странице «Обои» видно, сколько ПК показывают каждое изображение; по клику открывается реестр с этими ПК. Варианты одной картинки, сохранённые заново (другое сжатие или разрешение), показываются одной плиткой «N вариантов файла»: их объединяет перцептивный хэш миниатюры (dHash, расхождение до 10 бит из 64). Так выглядит `urfu-desktop.jpg`, который создаётся в профиле каждого пользователя под его экран: SHA-256 у копий разные, а картинка одна. В карточке ПК (вкладка «Оборудование») видно, что стоит, что назначено и применилось ли.

## Состав рабочего места и журнал оборудования

Агент с версии 2026.10.17 в каждом heartbeat присылает состав рабочего места (`hardware.components`, хранится в `hosts.hw_components`):

| Что | Откуда на ПК | Изменение |
|---|---|---|
| Материнская плата, BIOS | `Win32_BaseBoard`, `Win32_BIOS` | смена платы — журнал и алерт; обновление BIOS — только журнал |
| Модули памяти по слотам | `Win32_PhysicalMemory`: производитель, партномер, серийный номер, объём, частота | журнал и алерт |
| Физические диски | `Win32_DiskDrive` без USB-накопителей: модель, серийный номер, шина, объём | журнал и алерт |
| Видеокарты | `Win32_VideoController` (PCI); одна карта узнаётся по VEN/DEV и после смены драйвера | журнал и алерт |
| Мониторы | EDID из `WmiMonitorID`: производитель, модель, серийный номер, год, подключение (HDMI, DP, встроенный) | журнал; пропажа — алерт |
| Клавиатуры и мыши | `Win32_Keyboard`, `Win32_PointingDevice`: USB и HID, без PS/2-заглушек BIOS и устройств RDP; имя — от самого устройства | журнал; пропажа — алерт |
| Прочие USB-устройства | верхнего уровня, без хабов, накопителей и телефонов | только журнал |

- **Сравнение.** Сервер сравнивает снимок с прошлым (`services/workplace_devices.py`). Внутренние компоненты меняются только при вскрытии корпуса, поэтому их изменение фиксируется сразу. Пустой список памяти, дисков или видеокарт при непустом прошлом считается сбоем сбора, а не изъятием.
- **Периферию переподключают постоянно.** Её появление или пропажа подтверждается, только если держится 30 минут (`DEBOUNCE`). Пока не подтверждено, карточка показывает «не видно с …». Мышь, переставленная в другой порт, изменением не считается: ключ — VID:PID и серийный номер, а не порт.
- **Ограничение.** Одинаковые устройства без серийного номера (большинство мышей и клавиатур) различаются только количеством: подмену мыши на такую же модель не видно.
- **Журнал.** Таблица `hardware_events`, `GET /hosts/hardware-events?host_id=&days=&limit=`. В него же пишутся изменения модели, серийного номера, процессора и объёма памяти (`services/hardware_change.py`).
- **Алерты.** Смена внутренних компонентов — одним алертом `hardware_changed`. Подтверждённая пропажа клавиатуры, мыши или монитора — алертом `device_missing`.
- **После смены версии агента** снимок принимается заново, без сравнения: другая версия может собирать поля иначе.

Где видно:
- реестр, вид «Железо»: колонки «Видеокарта», «Монитор» и «Устр.» (клавиатура, мышь, монитор: на месте / пропало недавно / нет);
- фильтр «Оборудование»: нет клавиатуры или мыши, нет монитора, пропало недавно, изменения за 7 или 30 дней;
- карточка ПК, вкладка «Оборудование»: состав и журнал;
- «Обзор»: «Нет клавиатуры или мыши на N ПК в сети» и последние изменения по всему парку.

Серийный номер ПК из таблицы «Железо» убран: он есть в карточке, в поиске и в выгрузке CSV.

## Активация Windows и Office

Агент с версии 2026.10.17 раз в час присылает состояние активации (`hosts.license_activation`, `services/activation.py`):

- **Продукты Windows и Office** с установленным ключом: канал (KMS, MAK, Retail), состояние, причина (`LicenseStatusReason`) и сколько осталось — до конца пробного периода или до истечения KMS-активации.
- **Последнее обращение к KMS** по каждому продукту из журнала Application (события Security-SPP 12288/12289): куда, когда и с каким итогом. Office при неудаче повторяет попытку каждые 2 часа, Windows — раз в сутки.
- **Доступность KMS с ПК** — TCP-подключение к заданному вручную (`slmgr /skms`), последнему использованному или найденному через DNS KMS-серверу, порт 1688.
- **CMID** — у клонов образа без `sysprep /generalize` он одинаковый. Карточка показывает, у скольких ПК такой же; пока у KMS хватает других клиентов, активации это не мешает.

Сводка по каждому ПК — худшее состояние продуктов вида: «активирован», «истекает» (KMS-активация, до истечения меньше 30 дней — продление давно не проходит), «пробный период», «не активирован». Она видна в колонке «Активация» реестра (сортируется, проблемные — первыми), в фильтре «Активация» (не активирован Windows / Office, истекает, KMS недоступен, нет данных), одним пунктом в «Требует внимания» на «Обзоре» (активация Windows, Office и доступность KMS вместе: без KMS слетает и то и другое) и в выгрузке CSV. Подробности — в карточке ПК, раздел «Активация Windows и Office».

На октябрь 2026 года с подсетей SU5 (10.152.x) и SU7 (10.160.x) TCP 1688 до KMS университета (`sk5-cod-kms3.at.urfu.ru` / `kms.urfu.ru`, 93.88.176.5) не проходит, а из MR32 (10.40.x) проходит. Это сетевой фильтр: на самих ПК настраивать нечего.

## Группы хостов

Сервер сам раскладывает ПК по группам по имени, по той же схеме, что AutoDomain для OU: `КОРПУС-АУДИТОРИЯ-ТИП`, этаж — первая цифра номера аудитории.

`SU5-D206-TEMP` → `SU5` › `2 этаж` › `SU5-D206`

- ПК попадает в группу аудитории. Корпус и этаж — родительские группы; на странице хостов показаны путём, а фильтр по корпусу или этажу включает все аудитории внутри.
- Имя группы уникально внутри родителя, поэтому у каждого корпуса свой «2 этаж». В inventory Ansible (имена групп там глобальные) дерево вложено через `children`, а повторяющееся имя дополняется путём: `SU5 / 2 этаж`.
- Группы создаются по мере появления ПК: при регистрации агента, при каждом heartbeat (переименованный ПК переходит в группу новой аудитории) и раз в час для всех хостов, включая добавленные вручную и выключенные.
- Существующая группа с именем аудитории (например, ручная `MR32-411`) не дублируется: она встраивается в дерево под своим этажом.
- ПК, которого администратор положил в ручную группу с другим именем, остаётся там. ПК с именами вне схемы (`DESKTOP-…`, `WIN10-VDI000`) не трогаются.
- Опустевшая автоматическая группа удаляется сама: когда из аудитории ушёл последний ПК (переименование, перенос, удаление хоста или агента), удаляется она, а затем этаж и корпус, если в них тоже ничего не осталось. Проверка идёт сразу после изменения и при ежечасной раскладке. Не удаляются группы, которым задана учётка SSH, и группы, на которые нацелено расписание плейбуков — иначе молча пропала бы эта настройка. Ручные группы не удаляются никогда (`prune_empty_auto_groups` в `backend/services/host_grouping.py`).
- Учётная запись группы наследуется вниз по дереву: учётка, заданная корпусу, действует для всех его аудиторий, если у хоста и его группы своей нет. Задаётся на странице «Администрирование → Группы хостов». ПК с агентом подключаются своим ключом, выпущенным при регистрации, поэтому учётка группы действует только на ПК без агента. Ключ агента нельзя заменить или удалить, пока ПК им подключается; для SSH назначаются только SSH-ключ или логин с паролем, с логином (`backend/services/credential_rules.py`).
- Смена учётки SSH проверяется входом. Это касается своей учётки ПК (в карточке или массово: «Ещё → Учётные данные SSH»), учётки группы и переноса ПК, которые наследуют учётку, в группу с другой. Сервер сначала входит на каждый затронутый ПК новыми данными (`echo` по SSH, задача «Смена учётных данных SSH» с логом) и применяет изменение только там, где вход прошёл. ПК, на которых вход не прошёл (неверные данные или ПК выключен), остаются как были: со своей учёткой, в своей группе, а при смене учётки группы — на прежней учётке, которая назначается им напрямую. Если у ПК учётка не меняется, изменение применяется сразу, без проверки. Прямая смена через `PATCH /hosts/{id}`, `PATCH /hosts/groups/{id}` и перенос через `assign`/`unassign`, меняющий учётку, отклоняются — только `POST /hosts/access-changes` (`backend/services/access_change.py`).
- Автоматическая раскладка по аудиториям не переносит ПК, если он подключается учёткой своей группы и после переноса учётка сменилась бы; такой ПК остаётся на месте (в журнале backend — предупреждение).
- Запуск плейбука или расписание на корпус либо этаж охватывает все ПК его аудиторий. Группы расписания раскрываются при каждом запуске, поэтому новый ПК в аудитории попадает в расписание сам.
- Шаблон имени — `HOST_NAME_PATTERN` (регулярное выражение с группами `Building`, `Room`, `Floor`), отключить — `HOST_AUTO_GROUPING=false`.

## DNS

Сервер подключается к ПК по IP, который сообщает агент, поэтому от DNS работа не зависит. Имена нужны для диагностики и для всего, что обращается к ПК по имени.

- Агент сообщает короткое имя (`SU5-D206-TEMP`). backend и celery ищут его в `at.urfu.ru`, затем в `rtf.ustu` (`dns_search` в `docker-compose.yml`). `at.urfu.ru` идёт первым: ПК переезжают туда, а в `rtf.ustu` много устаревших записей, указывающих на адреса других ПК.
- DNS-серверы: `10.40.240.1` и `10.40.240.3` знают обе зоны, контроллер `at.urfu.ru` (`10.74.240.10`) — запасной. Основным его ставить нельзя: на `*.rtf.ustu` он отвечает «нет такого имени», а Docker при отрицательном ответе следующий сервер не спрашивает. Серверов не больше трёх — больше встроенный DNS Docker не использует.
- Этап DNS диагностики проверяет имя в каждом домене и сравнивает с IP агента: совпадение — успех, расхождение — предупреждение «stale DNS record».

## Установщик с вшитым токеном

«Администрирование → Агент и токены» → скачать установщик у токена. Это обёртка (NSIS) над тем же `FleetManagerAgent-Setup.exe`, который сервер подтягивает из GitHub Releases: она запускает его молча с `/ServerUrl` (`AGENT_PUBLIC_URL`) и `/EnrollmentToken`. Поэтому ПК получает текущую версию агента со всем, что ставит Inno-установщик: служба с восстановлением после сбоя, трей и панель управления, OpenSSH, RDP, Wake-on-LAN, запись в «Программах». Пока установщик не синхронизирован, скачивание отвечает 503.

- Запускать от администратора; для массовой раскатки обёртка понимает `/S` (тихо) и возвращает код выхода Inno Setup.
- Токен остаётся на ПК только в `agent.json`: временные файлы удаляются, а журнал Inno (в нём командная строка) сохраняется в `C:\ProgramData\FleetManagerAgent\logs\setup.log` с замаскированным токеном. Шаги установки — в `install.log` там же.
- При ошибке обёртка показывает код выхода Inno Setup с расшифровкой и пути к обоим журналам.
- Сам скачанный `.exe` содержит токен — храните его как пароль. Отозванный токен перестаёт регистрировать новые ПК.

## Версии агента

Установленная версия агента видна в реестре хостов (колонка «Агент», фильтр «Агент → Версия устарела») и в «Администрирование → Агент и токены»; доступная версия берётся из установщика, который сервер сам подтягивает из GitHub Releases. Проверка версии по SSH и удалённая установка свежего установщика поверх текущего запускаются с выбранных хостов: панель внизу страницы «Хосты» → «Ещё» — регистрация агента при этом сохраняется. Подробности API и механика обновления: [backend/README.md](backend/README.md).

Если до ПК не достучаться по SSH, обновление не теряется: сервер запоминает целевую версию (`hosts.agent_update_target`) и предлагает её агенту в ответе на heartbeat (`agent_update: {version, sha256}`), агент с 2026.10.24.24 скачивает установщик своим токеном и ставит сам. Агенты старше этой версии предложение не понимают — на них нужна одна установка на месте.

## SSH на ПК по отчёту агента

Агент каждые 5 минут присылает в heartbeat поле `ssh`: служба sshd (и отвечает ли она), правило брандмауэра для порта 22 с адреса сервера, GPO, игнорирующая локальные правила, `sshd_config`, машинный PATH, входит ли SSH-логин в локальные Администраторы, доверие с доменом и ключи хоста. Сервер хранит его в `hosts.ssh_state`, а причины, по которым он не попадёт на ПК, показывает в карточке хоста, раздел «SSH» (`services/ssh_health.py`). Что можно, агент чинит сам: автозапуск и зависание sshd, правило брандмауэра, PATH.

- OpenSSH Server нет вовсе (установщик считает сбой `Add-WindowsCapability` некритичным): агент присылает ошибку из своего `install.log`, а сервер в ответе на heartbeat предлагает ремонт — переустановку той же версии (`agent_update.repair`); sshd со всей настройкой ставит установщик. Агент делает не больше трёх попыток на версию.

- Пока по свежему отчёту SSH заведомо закрыт, heartbeat не забирает ожидающие задачи ПК — иначе они срывались на каждом heartbeat. Их заберёт проверка по SSH, когда он заработает.
- Если агент прислал ключи хоста, Ansible сверяет их по id хоста (`HostKeyAlias`, файл `ansible_data/keys/known_hosts/<id>`), а не по IP: после подготовки ПК из образа (новые ключи) или когда DHCP отдаёт адрес другому ПК, общий known_hosts давал «REMOTE HOST IDENTIFICATION HAS CHANGED».

## Алерты смены оборудования

Смену железа сервер определяет сам по heartbeat: сравнивает производителя, модель, серийный номер, процессор и объём памяти (в целых ГБ) с прошлым отчётом той же версии агента и пишет в алерт, что изменилось: «Память: 16 ГБ → 8 ГБ». Название ОС не сравнивается. Алерт агента `hardware_changed` (только два хэша отпечатка) принимается, но не сохраняется: у агентов до 2026.10.10.10 он срабатывал на смену языка названия ОС. Алерты видны в карточке хоста (вкладка «Алерты») и через фильтр «Алерты» на странице хостов; «Обзор» считает алерты за неделю.

## От чьего имени выполняются плейбуки

Сервер входит на ПК по SSH ключом Fleet Manager, который агент кладёт в `C:\ProgramData\ssh\administrators_authorized_keys`. OpenSSH на Windows принимает этот файл для любого члена локальной группы «Администраторы» (`Match Group administrators` в `sshd_config`), поэтому тем же ключом, без паролей, можно войти и под доменной учёткой (`backend/services/run_as.py`).

- **Плейбук, запущенный вручную**, выполняется от имени того, кто его запустил: `AT\<логин Windows>` (`LDAP_NETBIOS_DOMAIN`, по умолчанию `AT`). Это работает, если он вошёл в Fleet Manager доменной учётной записью и состоит в локальных администраторах ПК. На SU5 и SU7 в администраторах — группа `AT\IRITRTF OOD Staff`.
- **Проба перед запуском.** Каждый ПК задачи сначала пробуется входом под инициатором (`whoami`, параллельно `RUN_AS_PROBE_PARALLELISM`, по умолчанию 50). Где вход не прошёл (учётка не администратор ПК, отключена в домене, ПК недоступен, изменился ключ хоста), остаётся учётка, под которой ставили агент. Первый вход создаёт на ПК профиль пользователя — проба на это и рассчитана.
- **Расписание** выполняется от имени владельца: того, кто его создал или последним изменил. Правка чужого расписания делает владельцем правящего — иначе можно было бы запускать что угодно от чужой учётки. Расписания, созданные до этой возможности, идут от учётки установки.
- **Локальные пользователи Fleet Manager** и **фоновые задачи** (сканирование ПО, проверка и обновление агента, диагностика) — всегда от учётки установки агента.
- В начале лога задачи и в карточке задачи видно, от чьего имени она шла и на каких ПК и почему осталась учётка установки. В журнале безопасности Windows на ПК — реальный человек.
- Выключить: `PLAYBOOK_RUN_AS_INITIATOR=false`. Вход по ключу не даёт сетевых учётных данных (сетевые шары с ПК недоступны) — как и раньше с учёткой установки.

## Редактор плейбуков

Операторы и администраторы создают и правят плейбуки прямо в интерфейсе: «Автоматизация → Запуск», кнопка «+» рядом с выбором плейбука. Кнопка с иконкой файла открывает выбранный плейбук.

- **Хранение.** Новые плейбуки — локальные: отдельный источник «Fleet Manager» (`playbook_repos.kind = local`, каталог `LOCAL_PLAYBOOKS_DIR`, по умолчанию `/app/ansible_data/local_playbooks` в томе `ansible_data`, его видит и воркер Celery). В git они не попадают и живут только на этом сервере. Запуск, расписания и журнал задач работают с ними так же, как с плейбуками из репозитория.
- **Плейбуки из git** открываются только на просмотр: правка рабочей копии сломала бы следующий `git pull`. Кнопка «Сохранить копию в локальные» создаёт локальную копию; сам git-плейбук правят в репозитории.
- **Проверка.** Перед сохранением сервер разбирает YAML (ошибка — со строкой и позицией, строка подсвечивается в редакторе), проверяет, что это список play с `hosts`, и запускает `ansible-playbook --syntax-check`, который ловит неизвестные модули и ошибки ключевых слов. С ошибкой плейбук не сохраняется. Кнопка «Проверить» делает то же без сохранения.
- **Файлы.** Имя — латиница, цифры, `_`, `-`, окончание `.yml`; одна папка допускается (`install/firefox.yml`) и становится группой в каталоге. При переименовании расписания переезжают вместе с файлом. Плейбук, по которому есть расписание, не удаляется. Создание, правка и удаление пишутся в аудит.
- **Каталог** в форме запуска общий: плейбуки основного репозитория сгруппированы по папкам, локальные — группой «Fleet Manager».

## Алерт заполненности диска

Алерт `disk_full` (`backend/services/disk_alerts.py`) создаёт сервер, когда локальный диск ПК по heartbeat заполнен на `DISK_FULL_PERCENT` (90%) и больше: «Диск C: заполнен на 93%: свободно 8,2 ГБ из 119 ГБ». Алерт срабатывает один раз при переходе через порог, а не каждые 5 минут. Повторно диск даст алерт, только когда сначала освободится ниже `DISK_FULL_CLEAR_PERCENT` (85%), так что колебания около 90% алертами не сыплют. Диски в тревоге хранятся в `hosts.disk_alarms`. Такие ПК видны на «Обзоре» отдельным пунктом и в реестре через фильтр «Оборудование → Диск заполнен на 90% и больше».

## Переменные окружения

Смотрите `.env.example` — там описаны все обязательные секреты (JWT, Fernet-ключ для Key Store, параметры Postgres/Redis, CORS). `.env` в `.gitignore` — никогда не коммитьте реальные значения.

## Тесты

```bash
cd backend
python -m venv .venv && .venv/Scripts/activate   # или source .venv/bin/activate
pip install -r requirements.txt
python -m unittest discover -s tests
```

Тестам нужен заполненный `.env` в `backend/` (или переменные окружения) — `Settings` требует `jwt_secret_key` и `credential_encryption_key`; живая БД/Redis для этих тестов не нужны.

Фронтенд: `cd frontend && npm install && npm run build` (отдельного test-скрипта пока нет); проверка вручную — `npm run dev:mock`.
