# Обновление платформы

## Выпуск версии

В репозитории FleetManager-Server сценарий **Publish platform release** запускается вручную на `main` с новой версией `vX.Y.Z`. Он проверяет код, собирает два образа, проверяет точный серверный образ и миграции на пустой PostgreSQL, затем публикует готовый GitHub Release. Коммиты в `main` сами по себе релиз не выпускают. Ветки и предварительные релизы установщиком не поддерживаются.

Первый раз пакеты `fleet-manager-backend` и `fleet-manager-frontend` в GHCR нужно сделать публичными. Образы закреплены по digest, оба принадлежат одному релизу. Секреты сервера не передаются в GitHub Actions. GitHub Actions использует собственный `GITHUB_TOKEN` с правами публикации только в задании выпуска.

В Release входят `platform.json` (версия, коммит, схема БД, digest образов и SHA-256 архива) и `platform.tar.gz` (Compose и встроенные плейбуки). Не публикуйте релиз вручную до завершения загрузки обоих файлов. Не заменяйте файлы опубликованной версии; исправления выпускаются под новым номером.

## Первый переход

Требования: Linux с Python 3.12+, Docker Compose, curl; работающая установка с сервисами `backend`, `frontend`, `celery`, `celery-beat`, `postgres`, `redis`. Корень установки по умолчанию `/opt/fleet-manager`, Compose-проект `fleet-manager`. Для другого расположения измените параметры ExecStart в systemd unit до запуска. У процесса должны быть права управления Docker и чтения конфигурации установки.

1. Обновите исходники репозитория с новой службой, сохранив конфигурацию установки. Пересобирать работающие контейнеры для первого перехода необязательно: служба умеет обновлять прежнюю установку. В новом Compose backend получает каталог `/run/fleet-updater` только для чтения; сокет Docker приложению не нужен.
2. Из корня репозитория выполните `sudo sh updater/install.sh`. Код службы копируется отдельно от кода приложения; обычные релизы его не заменяют.
3. Проверьте `systemctl status fleet-updater` и `sudo python3 -m updater.service --request status` из `/opt/fleet-updater`.
4. Опубликуйте первый комплект и проверьте анонимное скачивание обоих образов. Если страницы обновления ещё нет, из `/opt/fleet-updater` выполните `sudo python3 -m updater.service --request install --version v1.0.0`. После установки страница «Администрирование → Обновление платформы» станет доступна; следующие версии можно устанавливать с неё.

Старая установка до первого обновления отображается без номера релиза. При первом переходе установщик сохраняет точные работающие образы под отдельными локальными тегами для возврата.

## Установка

Проверка GitHub выполняется раз в час и по кнопке. Установка запускается только администратором после подтверждения. При ошибке сети сохраняются сведения о ранее найденной версии.

Сначала скачиваются и проверяются файлы и образы, оценивается место для копии БД. Затем включается обслуживание, останавливается планировщик, воркер прекращает принимать новые задачи. Проверяется завершение активных, зарезервированных и отложенных задач. Нет ответа воркера или ожидание дольше 15 минут — установка откладывается, прежнее обслуживание восстанавливается. Плейбуки принудительно не прерываются.

После завершения задач останавливаются воркер и backend, создаются дамп PostgreSQL, копии конфигурации и локальных плейбуков. Миграции запускаются отдельным контейнером до запуска новой версии. Проверяются API, соединение с БД, frontend и ответ Celery. Только после этого запускается планировщик и снимается обслуживание.

Во время обслуживания запросы пользователей и агентов получают 503 с Retry-After. Статус обновления доступен, пока backend работает. При остановленном backend интерфейс временно теряет связь и продолжает проверять её восстановление. Журнал самой установки хранится независимо от приложения.

## Ошибки и восстановление

До изменения схемы БД возможен автоматический возврат. Если миграция завершилась успешно и схема осталась прежней, возврат образов также допустим. При сбое миграции, изменении схемы или неполадке восстановления сохраняется режим обслуживания. После перезапуска процесса во время критического этапа требуется явное восстановление: повторять миграцию вслепую нельзя.

Если страница работает, используйте кнопку восстановления и подтвердите замену БД копией. При неработающем backend восстановление запускается независимо от него:

```sh
cd /opt/fleet-updater
sudo python3 -m updater.service --request status
sudo python3 -m updater.service --request restore --confirm-data-loss
```

**Восстановление БД удаляет изменения после копии**, восстанавливает конфигурацию и локальные плейбуки. Если миграции ещё не начинались, служба возвращает предыдущие компоненты без замены БД. Резервная копия содержит конфиденциальные данные и хранится с доступом только для root.

Состояние и журнал: `/var/lib/fleet-updater/state.json`. Комплекты и копии: `/var/lib/fleet-updater/releases/<идентификатор>/`. Служебный журнал: `journalctl -u fleet-updater`. В случае непригодной копии используйте обычную процедуру аварийного восстановления; флаг обслуживания не удаляйте до проверки БД.

После перехода на релизы рабочий Compose указан в `current.compose` файла состояния. Не запускайте обновление через старый Compose из корня: он вернёт образы локальной сборки. При ручной диагностике используйте `docker compose --project-directory /opt/fleet-manager --env-file /opt/fleet-manager/.env -p fleet-manager -f <current.compose> ...`.

Копии и предыдущие образы автоматически не удаляются. Следите за местом и удаляйте только комплекты, которые больше не нужны для восстановления, сохраняя текущий и предыдущий рабочий комплект. Этот механизм не заменяет внешние резервные копии.

## Границы первой версии

Обновляются только компоненты FleetManager. Версии PostgreSQL/Redis и Windows-агентов этим процессом не меняются. Установки по расписанию нет. Совместимость с установленными агентами проверяется перед выпуском; изменение протокола требует отдельного плана перехода.
